# Final unified wall model deployment (V1 classifier, no-backflow couette) — OpenFOAM integration

Pure-C++ (no LibTorch, no Python at runtime) integration of the full
classifier + 5-regime blend wall model. Same architecture and usage as
`../V1 classifier updated Re selective data/` (itself a sibling of
`../Openfoam_integration_with_classifier/`), but with **two real changes**
relative to that immediate predecessor:

1. **Couette's regression building block is retrained on backflow-filtered
   data.** `../couette_data_aug_12/purge.py` removed 15 of the 56 nominal
   `(ReU, ReP)` conditions for having genuine flow reversal at the sampled
   points (see that script's own docstring for the per-condition averaged
   sign-of-outermost-point detection method, and
   `../updated couette no backflow building block/` for the retrain). This
   fixes a real bug, not just a minor accuracy tweak: couette's
   `tw_direction_angle` MAE drops from **0.278 to 0.040** (a ~7x
   improvement) — the removed conditions were the most extreme pressure-
   differential cases, exactly where the OLD data's near-`±π` wraparound
   values were blowing up the trained model's predictions toward 0.
2. **Crossflow's regression building block now matches what the classifier
   was actually trained to recognize.** The immediate predecessor
   (`../V1 classifier updated Re selective data/`) had a real, documented-
   but-not-fixed inconsistency: its classifier was trained on the full-scale
   (all 4 `Re_tau`) Aug-11 crossflow data, but the crossflow *regression*
   model it deployed was still the older, reduced-scale (2-of-4 `Re_tau`)
   one. This package uses the full-scale model for both — see
   `export_regimes_for_openfoam.py`'s own module docstring for the full
   explanation.

Everything else — the classifier's own architecture/training methodology,
the 6-input feature formulas (new `Re_center`/`Re_top` full wall-parallel-
speed convention), the couette circular-angle C++ support, the `sqrt_cols`
classifier transform support — carries over unchanged from that predecessor.
See `../V1 classifier updated Re selective data/README.md` for the full
history of how those pieces were established, if you need it; this README
covers what's specific to this package.

## 1. What you're integrating

```cpp
Foam::unifiedWallModel model("/path/to/wmLayers_openfoam");

std::vector<Foam::scalar> rawInputs = {
    Re_center, Re_top, ax_n, gamma12, lambda_roc, tke_n   // this exact order
};

auto pred = model.predict(rawInputs);
// pred.twMean, pred.twSigma, pred.angleMean, pred.angleSigma
// pred.weightsMean[5], pred.weightsSigma[5]   - label order below
// pred.weightsCov[5][5]                        - full covariance, if you need it
```

Regime label order (fixed everywhere): `0=laminar, 1=freestream, 2=channel,
3=couette, 4=crossflow`.

Construct `unifiedWallModel` **once**, call `predict()` once per
wall-adjacent cell/timestep.

**Path note:** `Foam::fileName` rejects paths containing spaces - keep
`wmLayers_openfoam/` somewhere space-free in your case/solver directory
structure (this project's own directory names have spaces; don't deploy
straight from here).

## 4. The 6 inputs - exact definitions

| # | Name | Formula | Notes |
|---|---|---|---|
| 0 | `Re_center` | `rho * sqrt(u(y_p)^2 + w(y_p)^2) * y_p / mu` | Full wall-parallel speed (streamwise `u` AND spanwise/transverse `w`). |
| 1 | `Re_top` | `rho * sqrt(u(2*y_p)^2 + w(2*y_p)^2) * 2*y_p / mu` | Same convention, evaluated at a point twice as far from the wall. |
| 2 | `ax_n` | `ax(y_p) * y_p^3 / nu^2` | Streamwise acceleration. |
| 3 | `gamma12` | `wrap(theta_top - theta_center)`, `theta = atan2(u, w)` | |
| 4 | `lambda_roc` | `dlambda/dt * y_p^2 / nu`, `lambda = atan2(w, u)` | |
| 5 | `tke_n` | `TKE(y_p) / mean_KE(y_p)` | Classifier applies `sqrt` to this column internally (via `input_metadata.txt`'s `sqrt_cols`) - feed the raw ratio, don't pre-transform it yourself. |

See `optimizer-couette/openfoam_integration_couette/OPENFOAM_INTEGRATION_GUIDE.md`
§4 for the full derivation (which point/frame to sample, wall-relative
conventions for Couette/crossflow, acceleration sign flips at moving walls)
if you're computing these from a live CFD field for the first time - it
hasn't changed.

## 5. Couette's circular `tw_direction_angle`

`angleModel` auto-detects, per regime, whether `tw_direction_angle/` holds a
plain single ensemble or a circular sin/cos pair, via `angle_type.txt`
(`"plain"` or `"circular"`) - never inferred from folder contents. Only
couette uses `"circular"` here; laminar/channel/crossflow all use `"plain"`.
Reconstruction formula:
```
angle_mean = atan2(mean_sin, mean_cos)
Var(angle)  = (mean_cos^2*var_sin + mean_sin^2*var_cos) / (mean_sin^2+mean_cos^2)^2
```

## 6. Regenerating this package if something is retrained further

1. **Couette retrained again**: rerun training in
   `../updated couette no backflow building block/` (or a successor
   directory), then rerun `export_regimes_for_openfoam.py` here (update its
   `SOURCES["couette"]` path first if the directory name changes).
2. **Crossflow retrained again**: rerun training in
   `lukas_cross_flow_download/cross_flow_building_block/`, then rerun
   `export_regimes_for_openfoam.py` here.
3. **Channel/laminar retrained**: same pattern - update the relevant
   `SOURCES[...]` path in `export_regimes_for_openfoam.py`, rerun it.
4. **Classifier retrained**: rerun `train_classifier.py` and
   `export_classifier_for_openfoam.py` in
   `../V1 classifier no backflow couette/`, then rerun
   `copy_classifier_export.py` here.
5. **Re-verify after any of the above**: `python3 generate_verification_rows.py`
   then `./compile_and_verify.sh` (needs a real OpenFOAM install - see that
   script's own env vars, currently set for `openfoam2412`/WSL/Linux).

## 7. Classifier accuracy

Architecture sweep winner: 3 layers, 128 hidden, tanh (same architecture the
immediate predecessor picked). Held-out accuracy **74.82%**
(`../V1 classifier no backflow couette/train_classifier.log` has the full
run):

| Class | Recall | n (held-out) |
|---|---|---|
| laminar | 100.00% | 120,000 |
| freestream | 93.41% | 29,448 |
| channel | 70.06% | 117,792 |
| couette | 48.75% | 120,000 |
| crossflow | 76.26% | 83,008 |

Compared to the immediate predecessor (`../V1 classifier updated Re
selective data/`, same architecture, only the couette source differs):

| Version | Overall | laminar | freestream | channel | couette | crossflow |
|---|---|---|---|---|---|---|
| predecessor (backflow-contaminated couette) | 76.31% | 100.00% | 94.23% | 73.57% | 50.76% | 76.55% |
| **this package** (backflow-filtered couette) | **74.82%** | 100.00% | 93.41% | 70.06% | 48.75% | 76.26% |

**Read this honestly: filtering out backflow did NOT improve classifier
accuracy - every class recall is flat or slightly down, including couette's
own (50.76% -> 48.75%).** This is a real result, not a bug in this run
(export self-check and the C++ verification in §8 both confirm the pipeline
itself is correct). A plausible explanation, not yet confirmed by further
testing: `purge.py` removes 15 **entire conditions**, not just the
individual backflow-affected sample points within them - and the removed
conditions are specifically the most extreme pressure-differential cases
(largest `|ReP|` at each `ReU`). Those extreme conditions were likely the
classifier's most distinctive, easiest-to-separate couette examples (a
strongly pressure-driven profile looks least like channel/crossflow
turbulence); removing them narrows the couette class down to its more
moderate, more channel/crossflow-overlapping conditions, at the SAME time
as removing a broad swath of otherwise-legitimate training signal (most
points within a purged condition were not themselves problematic - the
condition-level average of the outermost point is what triggered removal,
per `purge.py`'s own detection method). This is exactly why couette's
*regression* model (§0 above, `tw_direction_angle` MAE 0.278->0.040)
improved so dramatically while the *classifier* did not: the regression fix
specifically targeted the near-`±π` wraparound blowup at those extreme
conditions, while the classifier loses those conditions' distinctive
feature-space coverage entirely, with no offsetting benefit of its own.

**This is still the right classifier to deploy if you're deploying the
backflow-filtered couette regression model** - the alternative (this
classifier's couette class trained on conditions the couette regression
model itself no longer supports) would be a worse, silently-inconsistent
mismatch between what the classifier calls "couette" and what the deployed
couette model was actually trained on. The accuracy drop is the honest cost
of that consistency, not a sign anything is broken.

## 8. Verification

Compiled against a real OpenFOAM v2412 installation (`openfoam2412`
package, WSL, `WM_OPTIONS=linux64GccDPInt32Opt`, `-std=c++14`) via
`compile_and_verify.sh`: 5 real rows from `../V1 classifier no backflow
couette/classifier_training_data_no_backflow.npy` - one genuine example from
*each* of the 5 regimes - fed through both the Python reference
(`generate_verification_rows.py`/`reference_blend_predict.py`) and the
compiled `unifiedWallModel` (`test_main.C`). Matched to **8.55e-06 max
absolute difference** across `tw`/angle predictions, their sigmas, and all 5
weights - the same double-vs-float32 arithmetic precision floor as every
other integration in this project. Weight sums verified exactly `1.0` on
every row (`weightSum=1` for all 5 rows in `compile_and_verify.log`).

Row 3 (the couette example) happened to land on a genuine misclassification
(83.75% weight assigned to crossflow, not couette) - left in rather than
re-rolled, since it's still a fully valid test of forward-pass correctness
(and an honest, representative illustration of §7's 48.75% couette recall,
not a cherry-picked "good" example).

## 9. Caveats worth knowing before deploying this

- **"Freestream" has no separately-trained model** - aliases channel's
  prediction.
- **Channel/Couette/crossflow genuinely, physically overlap** in this
  6-input space - classifier weight uncertainty (`weightsSigma`/
  `weightsCov`) is real, load-bearing information, not just decoration.
- **`tw_direction_angle` is combined across regimes with a plain circular-
  resultant-vector average** (`reference_blend_predict.py`'s
  `_combine_circular` / the equivalent C++ in `unified_wall_model.C`) - this
  is correct circular statistics for the cross-regime blend, distinct from
  (and not to be confused with) couette's own internal sin/cos ensemble
  combine, which happens *inside* that regime's deployable before the blend
  ever sees it.
- **Couette's own coverage gap**: `updated couette no backflow building
  block/`'s 41-of-56-condition set still excludes the same 15 conditions
  everywhere downstream (regression model AND classifier training data) -
  this is a deliberate, physically-motivated exclusion (genuine backflow at
  those points, not noise), not a data-scarcity accident, but worth knowing
  if your case sits specifically in one of those 15 corners
  (`ReU∈{3000,5000,7500,10000}` combined with the most extreme `|ReP|`
  values, plus a few others - see `../couette_data_aug_12/purge.py`'s own
  output for the exact list).
- **Crossflow's classifier training data still excludes all three
  `Re_tau=180` conditions** (`sin_180`, `random_180`, `step_180`) -
  Charbel's own explicit request, unchanged from the immediate predecessor.
  The crossflow *regression* model itself, however, is trained on its full
  6-condition set (all 4 `Re_tau`, including 180) - only the classifier's
  training data is restricted.
- **Two `classifier_w_<regime>_mean` fields reading identical at a given
  wall point is expected, not a bug** - it means the classifier assigned
  zero evidence to both regimes there, which ties them at the same floor
  weight; verified this is genuine model behavior, not an indexing mistake
  in the field-writing code - see §10.1.

## 10. Uncertainty propagation - `(C,Z)`-calibration-driven `twSigma`

`twSigma` now includes a real, new source of uncertainty on top of what was
already here (each regime's own NN aleatoric+epistemic, the classifier's own
regime-selection uncertainty): how much each regime's trained model would
have differed had ODT's `(C,Z)` eddy-model constants been drawn from a
different, still-plausible point in their calibration's own posterior,
instead of the single best-fit point actually used to generate its training
data. Full methodology, LHS design, the real 320-run ODT campaign that
produced these numbers, and diagnostic plots (saved for reporting) are in
`../Uncertainty_propagation/README.md` - this section only summarizes the
result and what changed here.

**`tau^2` values** (`wmLayers_openfoam/cz_uncertainty.txt`):

| Flow | tau^2 | tau (std) | 90% CI on tau^2 |
|---|---|---|---|
| channel (also used for freestream, crossflow) | 6.980734e-03 | 0.0836 | [3.916e-03, 9.823e-03] |
| couette | 2.625367e-02 | 0.1620 | [1.630e-02, 3.440e-02] |

Derived from 320 real ODT runs (32 LHS `(C,Z)` points x 5 repeats x
1,000,000 timesteps, per flow type) via a one-way random-effects ANOVA that
cleanly separates this signal from ODT's own run-to-run stochastic noise (F
= 198 and 733 respectively - unambiguous, not a marginal detection).

**Effect on `twSigma`** (the 5 verification rows, before -> after writing
real values into `cz_uncertainty.txt`):

| Row (true regime) | twSigma before | twSigma after |
|---|---|---|
| laminar | 0.001178 | 0.001208 |
| freestream | 0.040193 | 0.073567 |
| channel | 0.020117 | 0.068862 |
| couette | 0.103737 | 0.125826 |
| crossflow | 0.262470 | 0.268563 |

**For channel/freestream specifically, `(C,Z)` uncertainty is now the
dominant contributor to `twSigma`** - roughly 3x the NN-only value. Re-
verified end to end after writing the real values (not just the earlier
zero-default check): max abs diff vs the Python reference is still
8.5472e-06 (same floor as always), and `angleSigma` is confirmed
byte-identical to the pre-patch package at every row - `tw_direction_angle`
is untouched, exactly as scoped.

**Implementation**: `tau_i^2` is added directly onto each regime's own
`sigma_i^2` before the existing, unmodified `combine()`/`_combine()` formula
runs (both C++ and Python read the same `cz_uncertainty.txt` - see that
formula's own comments in `unified_wall_model.C` and `reference_blend_
predict.py` for the re-derivation showing this needs no structural change to
the combination logic itself). `tw_n_sigma` (the fully-combined result) and
`tw_n_mean` (the model's own mean prediction) are now written into registered
`volScalarField`s by `mlNutUWallFunctionFvPatchScalarField.C` (§2) instead
of being discarded into a debug log - **built and verified against a real
OpenFOAM-13 solver run, see §11**.

### 10.1 Classifier weight fields (added 2026-08-20) - visualizing the classification itself

Everything above concerns `twSigma`/`twMean`, the *blended* prediction - not
the classifier's own regime breakdown that produced it. That breakdown
(`values.weightsMean`/`weightsSigma`, `unified_wall_model.H`'s `Prediction`
struct) was already computed on every call - `unifiedWallModel::predict()`
always classifies before blending - but previously discarded the moment
`combine()` used it, never written anywhere a user could see it. Charbel
asked specifically to be able to probe a wall point in ParaView and read
off its classification (e.g. "20% couette, 50% laminar") - that needed the
weights exposed as their own fields, not just folded into `twSigma`.

**10 new registered fields**, written by the same lazily-created-field
machinery as `tw_n_mean`/`tw_n_sigma` (`writeTwField`, now called through a
small `writeClassifierWeightFields` wrapper so all 5 regimes write in one
call per face) - label order fixed to `RegimeLabel`
(`unified_wall_model.H`), never reordered:

| Field | Meaning |
|---|---|
| `classifier_w_laminar_mean` | Mean weight (0-1) the classifier assigns to "laminar" at this face |
| `classifier_w_freestream_mean` | ...to "freestream" |
| `classifier_w_channel_mean` | ...to "channel" |
| `classifier_w_couette_mean` | ...to "couette" |
| `classifier_w_crossflow_mean` | ...to "crossflow" |
| `classifier_w_<regime>_sigma` (x5) | The classifier's own marginal uncertainty on each of the 5 weights above (`values.weightsSigma`) - large exactly where the classifier itself is unsure, independent of whether the *blend* ends up confident |

**To use in ParaView**: open the case's `.foam` file, select a wall patch,
use Point/Cell probe (or Plot Over Line along the wall) and read the 5
`classifier_w_*_mean` fields at any point - they sum to 1.0 there (verified
below), so reading all 5 gives the exact classification breakdown, e.g.
"38% couette, 25% crossflow, 16% freestream, 10% laminar, 10% channel."
Color a wall surface by any single one of the 5 mean fields to see where in
the domain that regime dominates; the `_sigma` fields show where the
classifier itself is least confident, which is not always the same place.

**Verified, not just written**: rebuilt against OpenFOAM-13 and rerun on
`verification_case_openfoam13/` (§11.1's own process) - `classifier_w_*_mean`
sums to `1.0` (to float precision, e.g. `1.000001`) at every one of the
1200 faces on both wall patches, exactly the "weight sums to unity" check
§8 already established for the standalone model. Went further than that,
though: pulled the exact 6 raw inputs the solver itself used for one real
face (`nutwmlog.log`'s own debug trace), fed them through the independent
Python reference (`reference_blend_predict.py`) completely separately from
the compiled OpenFOAM run, and got an **exact match** (bottomWall face 0:
laminar=0.103686, freestream=0.159845, channel=0.103686, couette=0.382725,
crossflow=0.250058, matching the field file to every printed digit; same
for a topWall face). This is a direct, per-face, real-solver-input
cross-check, not just an aggregate sanity check.

That cross-check also resolved a real "is this a bug" question honestly
rather than assuming: `classifier_w_laminar_mean` came out **exactly equal**
to `classifier_w_channel_mean` at most (not all) faces in this specific
case. Confirmed via the same independent Python reference (run separately,
on synthetic inputs unrelated to this case) that this is genuine evidential-
classifier behavior, not an indexing bug: whichever regimes get zero raw
evidence for a given input legitimately tie at the same floor weight
`1/(sum(evidence)+K)` - which *specific* pair ties changes face to face (one
face in this exact run tied `channel`==`freestream` instead, with `laminar`
clearly different and large) - a fixed indexing bug would tie the same pair
unconditionally, not one that varies with the input. Worth knowing before
reading a tie as "these two fields must be aliased."

## 11. Building a real, working library and verifying it end to end

This directory is now a self-contained wmake project (`Make/files`,
`Make/options`) - `wmake libso .` (from an environment with an OpenFOAM
install sourced) builds `libUnifiedWallModel.so` from every `.C` file here,
including `mlNutUWallFunctionFvPatchScalarField.C`. This section documents
what actually got built, tested, and run - not just written.

### 11.1 OpenFOAM-13 (Foundation) - built, and verified with a real solver run

**Built successfully.** Two real bugs were found and fixed - both in
pre-existing code, not in anything from §10:

1. **`mesh.time().timeName()` doesn't exist in OpenFOAM-13.** Foundation
   renamed this to `mesh.time().name()` (confirmed via Foundation's own
   `wallDist.C`, which uses `mesh.time().name()` for the exact same
   lazily-created-field pattern this code needed). Fixed with a compile-time
   switch on the `OPENFOAM` macro (defined by ESI's own wmake, absent under
   Foundation):
   ```cpp
   #ifdef OPENFOAM
       mesh.time().timeName(),
   #else
       mesh.time().name(),
   #endif
   ```
2. **An unconditional `db().lookupObject<volScalarField>("rho")` lookup
   crashed every incompressible solver.** `rho`/`rhop` were computed but
   used ONLY in two already-commented-out lines (confirmed via `grep` before
   touching anything) - genuinely dead code, safe to remove outright. This
   wasn't a hypothetical risk: a real end-to-end run against `foamRun`'s
   `incompressibleFluid` solver aborted here with `request for
   volScalarField rho ... failed` before the fix, and ran clean after it.

**Verification case** (`verification_case_openfoam13/`, built from
OpenFOAM-13's own `tutorials/incompressibleFluid/channel395` - a real
turbulent channel flow at Re_τ≈395, LES/WALE, periodic streamwise/spanwise,
40×25×30 mesh): changed `bottomWall`/`topWall`'s `nut` boundary type from
`zeroGradient` to `mlNutUWallFunction`, pointed `constant/wallModel_
classifier` at this package's own `wmLayers_openfoam/`, added `libs
("libUnifiedWallModel.so");` to `controlDict`, shortened `endTime` to 5
timesteps for a fast check. Ran `blockMesh` then `foamRun` for real:

```
foamRun_exit=0
"nutU wall function loop" printed twice per timestep (both wall patches, confirmed invoked)
```

**`1/tw_n_sigma` exists** - a genuine, registered, ParaView-openable field,
alongside `U`, `p`, `nut`, `k`. 2400 boundary values (2 patches x 1200 faces),
zero NaN/Inf, range `[0.0446, 5.544]` - finite, positive, physically
reasonable magnitudes consistent with the standalone verification rows in
§8/§10. This is the strongest evidence in this package that the whole
pipeline - classifier, all 4 regime models, the `(C,Z)` term, and now the
OpenFOAM field-writing itself - genuinely works, not just compiles.

**`tw_n_mean` added afterward (2026-08-15), for `../LES_Channel_test/`'s own
comparison study**: the model's actual `values.twMean` prediction, exposed
the same way `tw_n_sigma` already was (`writeTwUncertaintyField()` was
generalized to `writeTwField(..., fieldName)`, called twice) - the earlier
work only ever exposed the *uncertainty*, not the mean prediction itself.
`compiled_libs/openfoam13/libUnifiedWallModel.so` and `verification_case_
openfoam13/` were both regenerated after this change (re-run from a WSL-
native copy - `foamRun` genuinely crashes with `fileName::stripInvalid()`
when run directly against a `/mnt/c/...` path containing spaces, unlike a
plain compile, which tolerates it fine - see this same issue's original,
more detailed writeup from earlier mesh-debugging work in this project if
you hit it elsewhere). `tw_n_sigma`'s values matched the original run

To reproduce: `source <OpenFOAM-13 install>/etc/bashrc`, `wmake libso .`
from this directory, then in `verification_case_openfoam13/`: `blockMesh &&
foamRun`.

### 11.2 OpenFOAM v2412 (ESI) - NOT completed, honest account of why

The `openfoam2412` install available for this work turned out to use an
older API than the code in §10 was originally written against - and the
gap is deeper than a header rename:

- `momentumTransportModel.H`/the `momentumTransportModel` class do not
  exist anywhere in this install (confirmed via the installed package's
  own complete file manifest, not just a directory search) - this specific
  v2412 build uses `turbulenceModel.H`/`turbulenceModel` instead (the
  older ESI/Foundation-shared naming).
- That much is a clean swap. But `turbulenceModel::y()` returns
  `nearWallDist`, which derives from `volScalarField::Boundary` - NOT
  `volScalarField` - so it can't bind to the existing code's `const
  volScalarField& yField = turbModel.y();` at all; call sites would need
  `yField[patchi]` instead of `yField.boundaryField()[patchi]`, a real
  usage-pattern change, not a type alias.
- `turbulenceModel::yb()` (used in `yPlus()`) has no equivalent in this
  class at all - what replaces it would need further investigation.

Given OpenFOAM-13 - the version explicitly asked for - is fully built and
verified end to end, and given the v2412 gap needs genuine, careful
rewriting (not a find-and-replace) with real risk of a silent correctness
bug if rushed, this was stopped here rather than pushed through under time
pressure. If v2412 support against this specific install is needed later,
start from the three bullet points above - they're the complete list of
what's actually blocking it, not a guess.
